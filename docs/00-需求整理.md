---

## 1. 一句话结论

**可以做，而且不需要等 SDK。** WT9011DCL-BT50 是 BLE 设备（不是 RS-485 串口设备），
Windows + Python + `bleak` 足以完成「连接 → 解析姿态 → 判断 → 输出指令」的全链路；
真正的风险不在代码，而在三个硬件参数（Notify UUID、帧格式、量程）和蓝牙链路的时延稳定性。

## 3. 事实状态：已确认 / 待核对 / 需要修正

### 3.1 已确认

- 型号后缀 `BT50` 代表蓝牙 5.0（BLE），**不能**按 RS-485 串口设备处理。
- 输出内容包含三轴加速度、三轴角速度、三轴姿态角；磁场需设备配置后才有意义。
- 官方标注输出频率 0.2–200 Hz，实际可达速率取决于设备配置、BLE 连接间隔和主机。
- Python 侧使用 `bleak` 即可，无需厂商驱动。

### 3.2 必须在实物上核对（代码已做成可配置）

| 项目 | 为什么必须核对 | 核对手段 |
| --- | --- | --- |
| Notify 特征值 UUID | 不同固件不同；UUID 猜错就是 0 数据 | `wt901 run --dump-hex` 打印已发现服务 |
| 帧格式（`0x61` 20 字节 还是 `0x51/52/53` 11 字节） | 决定解析分支 | `wt901 analyze --file capture.hex` |
| 量程（±16 g / ±2000 dps / ±180°） | 比例系数错 → 数值整体缩放错 | 水平静置应约 1 g、已知倾角对照 |
| 上电是否自动推流 | 部分模块需要先写使能指令 | 连接后 2 秒内是否有通知 |
| 稳定输出速率与端到端时延 | 决定控制周期上限 | `[stat]` 行的 rate / jitter_p95 |

### 3.3 需要修正的几处（原稿里的坑）

1. **分帧不是 9 字节。** `0x55 0x51` 标准帧是 11 字节：2 字节头 + 6 字节数据 +
   2 字节温度（`0x53` 是版本号）+ 1 字节校验和。按 9 字节解析会永久错位。
2. **20 字节的 `0x61` 帧没有校验字节。** 2 + 9×2 = 20，正好没有余量。所以这类帧
   做不到"校验和校验"，只能做量程合理性检查 + 统计异常率。想要端到端校验，得让设备
   输出 11 字节分帧（带校验和）。
3. **自动挑 Notify UUID 不可靠。** 设备常常同时暴露电池、串口透传等多个可通知特征值，
   正式部署必须写死 UUID。
4. **原程序"断开 0.5 秒后才 STOP"不够。** 断线事件本身就应该立刻下发 STOP，超时只是
   第二道防线；本项目两层都做了。
5. **`print` 不是产品接口。** 需要明确的输出契约（谁发、发什么、心跳、失效语义）。

## 4. 技术路线（四个决策）

| 决策 | 选择 | 理由 | 放弃了什么 |
| --- | --- | --- | --- |
| D1 分层 | 协议 / 状态 / 控制 / 输出四层解耦 | 换硬件、换执行器不用改核心 | 单文件脚本的"简单" |
| D2 控制节拍 | 通知流只更新"最新值"，控制环按固定 50 Hz 跑 | BLE 到达抖动不进控制周期 | 事件驱动（延迟低但抖动大） |
| D3 失效语义 | 无新数据 > `stale_timeout` 即 STOP，且 `valid=false` | 宁可停机，不可保持旧指令 | "保持上一状态"的平滑性 |
| D4 输出 | 可插拔 Sink，TCP 用有界队列 + 心跳 | 下游可以是 TCP/串口/PLC，且不阻塞采集 | 直接调用硬件 API 的耦合写法 |

## 7. 还需要你拍板的三件事

1. **控制对象是什么？** STM32/ESP32、PLC、电机/云台/伺服，还是 Windows 上另一个软件。
   决定 `sinks.py` 里接哪一个（TCP 已经可用，串口和 Modbus 预留）。
2. **控制量用哪个？** 默认 Pitch ±15°，但实际可能是 Roll、某个夹角，或者角速度。
3. **采样率要求多少？** 50 Hz 足够做姿态控制；要到 100–200 Hz 需要先测蓝牙链路的
   实际吞吐和抖动，不能只看传感器标称值。

## 8. 安全边界（请写进产品文档）

- Windows + BLE 不是硬实时链路。定时器粒度约 15.6 ms，链路时延受系统负载影响，
  **不适合**做有严格确定性时延要求的闭环控制。
- 本软件不替代执行机构一侧的硬件限位、急停按钮和独立看门狗。
- 涉及人员或设备安全的场景，STOP 必须由执行器自己判断（通信丢失即停），
  不能只依赖上位机"记得发 STOP"。
