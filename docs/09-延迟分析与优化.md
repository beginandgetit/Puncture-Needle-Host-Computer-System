# 延迟分析与优化（第一性原理）

> 现象：静止时还能接受，快速移动时上位机画面滞后可到 **1000 ms 以上**。
> 结论：这不是单一“蓝牙慢”，而是**采样周期 + 传输 + 渲染 + 队列**的叠加；
> 其中 **渲染服务时间接近/超过采样周期** 会让队列持续增长，延迟随运动时间累积。
> 本文件记录测量、模型、已实施修复和仍需现场确认的部分。

---

## 1. 延迟分解

一次“真实针动一下 → 屏幕上的针动一下”的延迟：

```text
T_total = T_sample + T_ble + T_os + W_queue + T_paint
```

| 环节 | 典型量级 | 说明 |
| --- | --- | --- |
| `T_sample` | 0–100 ms（10 Hz） | 设备融合/输出周期；平均半个周期 |
| `T_ble` | 15–50 ms（正常） | 连接间隔、通知排队、重传；异常时可到数百 ms |
| `T_os` | 1–16 ms | Windows 调度、WinRT 回调、线程切换 |
| `W_queue` | **可变，可能是主因** | 消费者（GUI）跟不上生产者时的排队等待 |
| `T_paint` | 25–85 ms（本机实测） | QPainter 对模型的顶点变换、排序、逐面绘制 |
| 平滑 | 20 ms（现设置） | `smoothing_s` 的群延迟 |

注意：`ImuReading.t_mono` 是**收到 BLE 字节并解码的时刻**，不是传感器采样时刻。
所以状态栏的“主机延迟”严格说是“到达→显示”，不包含设备内部融合和空中传输；
真正的“传感器→显示”需要外部刺激（LED/光电/敲击）做同步测量。

## 2. 为什么快速移动会到 1 秒：队列

设采样周期 `T`（10 Hz → 100 ms），单帧渲染服务时间 `S`，利用率：

```text
ρ = S / T
```

- `ρ < 1`：队列稳定，平均等待约 `ρ/(2(1-ρ))·S`（M/D/1 近似）；
- `ρ ≥ 1`：**队列无界增长**，每秒积压约 `1/T − 1/S` 帧。

例子：

| 采样 | 渲染 `S` | `ρ` | 结果 |
| --- | --- | --- | --- |
| 10 Hz (100 ms) | 85 ms | 0.85 | 平均等待已可达数百 ms，抖动时溢出 |
| 10 Hz | 120 ms | 1.20 | 每秒积压约 1.7 帧 → 约 6 s 后 1 s |
| 10 Hz | 200 ms | 2.00 | 每秒积压 5 帧 → **约 1 s 后就 1 s** |
| 50 Hz (20 ms) | 85 ms | 4.25 | 若仍逐帧排队，几秒内爆到数秒 |

这解释了“为什么移动快时更明显”：

1. 延迟本身是队列/固定延迟，快速移动让**旧姿态与新姿态差异更大**，人眼立刻看出；
2. 如果每来一帧就触发一次重绘，而重绘 `S > T`，队列只会越来越长；
3. 50 Hz 并不会自动变快——**如果消费者不合并，反而更快积压**。

## 3. 本机实测的渲染成本

离屏 `QPainter`，1400×860 窗口，三个视图都绘制模型：

| 模型面数 | 单主视图 `grab()` | 整窗 `grab()` |
| --- | --- | --- |
| 8000 | ≈ 58 ms | ≈ 85 ms |
| 2667（简化后） | ≈ 25 ms | ≈ 42 ms |

8000 面时，10 Hz 的 `T=100 ms` 已经接近 `S=85 ms`，任何抖动都会让队列溢出；
目标工控机更慢时，`S` 很容易超过 100 ms。**这是 >1 s 的最可能主因。**

## 4. 已实施的修复

### 4.1 GUI 改成“最新值覆盖”，不再逐帧排队

`gui/worker.py`：

- 工作线程只把**最新一帧**放进加锁的 mailbox；
- 不再每个 BLE 帧发一个 Qt queued signal（那会形成无界事件队列）；
- GUI 用 `QTimer` 以约 30 fps 轮询 mailbox，中间帧主动丢弃。

`gui/window.py`：

- `_poll_reading()` 只取 `worker.latest()`；`seq` 相同则跳过；
- 记录 `跳过` 计数（`seq` 跳过的数量），状态栏可见；
- `_on_reading` 使用 `reading.t_mono` 作为时间基准，避免把排队时间算进平滑。

效果：延迟上限从“随运动时间增长”变成“约一个轮询/绘制周期”，**不会累积到 1 s**。

### 4.2 降低单帧渲染成本

- CAD 模型简化上限从 8000 面降到 **3000 面**（`MODEL_MAX_FACES`）；
- 两个小视图的模型简化到 **600 面**；
- 状态栏显示 `渲染 xx ms`，可直接看到目标机上的真实成本。

如果要进一步降到 <10 ms，下一步是把 `QPainter` 软件渲染换成 `QOpenGLWidget`/Qt3D；
当前先用降面数 + 合并帧把队列问题止住。

### 4.3 降低平滑延迟

`smoothing_s` 从 60 ms 降到 **20 ms**。60 ms 是直接的群延迟，快速移动时非常明显；
如果 50 Hz 数据稳定，可以设为 0，用原始四元数显示。

## 5. 现场还需要做的两件事

### 5.1 确认 BLE 传输本身是否正常

在 GUI 状态栏看：

- `主机延迟`：到达→显示的年龄；正常应稳定在几十 ms，不应持续增长；
- `跳过`：如果持续快速增长，说明渲染仍慢于轮询；延迟应仍有界；
- `渲染`：目标机上的单帧成本；若 >50 ms，优先降面数/换 OpenGL。

如果 `主机延迟` 仍然周期性跳到 ~1000 ms，且 `跳过` 不大，则问题在 **BLE 连接间隔/通知排队**，
而不是 GUI。用 `probe` 记录通知到达间隔：

```powershell
python -m wt901 probe --name WT901BLE67 --duration 10
```

`probe` 现在会打印通知到达间隔的 **p50 / p95 / max**（`notify interval`）。
若 p50≈100 ms、p95 也接近 100 ms，传输正常；若 p95 或 max 出现 ~1000 ms 的尖峰，
而帧率仍显示 10 Hz，说明通知被连接间隔/从机延迟“攒批”了。需要：

- 关闭 Windows 蓝牙适配器的省电模式；
- 换 USB 蓝牙 dongle，远离 2.4 GHz Wi-Fi/USB3 干扰；
- 确认没有厂商上位机/手机同时占用链路；
- 必要时用 WinRT 的 `BluetoothLEPreferredConnectionParameters` 请求低延迟连接参数
  （`bleak` 公共 API 不暴露，需要平台特定代码）。

### 5.2 提高设备输出率（在 GUI 稳定之后）

10 Hz 本身意味着平均 50 ms 的采样延迟。链路和 GUI 都稳定后，可把设备设到 50 Hz：

```powershell
python -m wt901 rate --hz 50 --save
```

或按维特协议写寄存器：`FF AA 03 08 00 B4`（50 Hz），`FF AA 00 00 00 A9` 保存。
注意：**必须先完成 4.1 的合并帧**，否则 50 Hz 只会让队列更快积压。

## 6. 验收标准（建议）

| 场景 | 目标 |
| --- | --- |
| 静止，10 Hz | 状态栏 `主机延迟` < 150 ms，`跳过` 不持续增长 |
| 快速往复移动 10 s | `主机延迟` 不随时间单调增大；画面不“越动越滞后” |
| 50 Hz（链路正常） | `主机延迟` < 100 ms；`渲染` < 50 ms |
| 拔掉/远离设备 | 0.4 s 内变灰/NO DATA，不保留旧姿态 |

> 真实“传感器→显示”延迟需外部同步测量；状态栏只能证明**到达→显示**这一段。
> 先把这一段压到稳定，再用外部刺激测总延迟，才能判断 BLE/设备融合占了多少。
