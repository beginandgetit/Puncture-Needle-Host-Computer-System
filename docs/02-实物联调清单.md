# 实物联调清单

按顺序做，每一步都有明确的"通过标准"。任何一步不通过，先看最后的排查表，
不要跳到下一步去调控制参数。

> 全程只开一个程序占用传感器：手机 App、厂商上位机、上次没退干净的 Python 进程
> 都会抢占 BLE 连接，表现为"能连上但收不到数据"。

---

## 步骤 0：环境确认

- [ ] Windows 蓝牙已打开，设备管理器里没有黄色感叹号
- [ ] 传感器电量充足（低电压时输出会异常）
- [ ] 关闭手机 App、厂商上位机
- [ ] 已验证离线链路：`python -m wt901 selftest` 全部 PASS

## 步骤 1：扫描并记录地址

```powershell
python -m wt901 scan
```

通过标准：列表里能看到名字含 `WT901` 的设备。

- 记录 **地址**（`AA:BB:CC:DD:EE:FF`）与 **名称**。
- 如果扫不到：先确认传感器已开机且在广播（有的型号连接过手机后需要重新上电）。
- 如果 Windows 蓝牙设置里显示"已配对"但扫描列表里没有：厂商上位机可能把它切成了
  SPP/虚拟串口模式，此时它不是 BLE 设备。关掉上位机、重新上电再扫；仍不行就按串口方案处理。

## 步骤 2：连接并抓原始流

```powershell
python -m wt901 run --address AA:BB:CC:DD:EE:FF --capture raw.bin --dump-hex
```

通过标准：

- 打印出 `Service:` / `char` 列表，并出现 `[ble] subscribe <uuid>`
- 出现 `[raw] ...` 行，且 `[stat]` 里 `ok` 持续增长

**记录实际使用的 Notify UUID**。如果提示"multiple notify characteristics"，
从打印的列表里挑出**数据流量最大**的那个，用 `--notify-uuid` 固定下来。

```powershell
python -m wt901 run --address AA:BB:CC:DD:EE:FF --notify-uuid 0000ffe1-0000-1000-8000-00805f9b34fb
```

## 步骤 3：确认帧格式

```powershell
python -m wt901 analyze --file raw.bin --limit 5
```

通过标准：`kind` 只有一种，且 `bad_sum=0 bad_hdr=0`（`dropped` 少量可接受）。

| 现象 | 结论 | 处理 |
| --- | --- | --- |
| `ok>0`，`kind=combined`，`frames_by_id` 只有 `0x61` | 设备输出 20 字节合并帧 | 默认配置即可 |
| `ok>0`，`kind` 在 accel/gyro/angle 之间轮转 | 设备输出 11 字节分帧 | 默认配置即可，三帧会被自动合并 |
| `ok=0`，`bad_hdr` 很大 | 帧类型假设错误 | 把 raw.bin 的前 64 字节贴出来再判断 |
| `ok>0` 但 `bad_sum` 持续增长 | 帧长/校验假设错误 | 尝试 `--combined-checksum`；分帧则检查是否真的是 11 字节 |

> 合并帧没有校验字节，`bad_sum` 恒为 0 是正常的，不代表"链路完美"。

## 步骤 4：核对量程（最容易错的一步）

水平静置传感器，观察 `[data]` 行：

- [ ] `az ≈ 1.00`（±0.05），`ax ≈ 0`，`ay ≈ 0`
- [ ] 静置时 `roll ≈ pitch ≈ 0`，`yaw` 可以是任意值
- [ ] 三轴角速度接近 0（有缓慢漂移正常）

若 `az ≈ 16` 或 `0.06` 之类，说明量程比例不对：用 `Scales` 改
`accel_g / gyro_dps / angle_deg`（见 `protocol.Scales`），不要直接改控制逻辑。

用已知倾角复核角度：把传感器沿 X 轴倾斜 30°，`pitch` 应约为 ±30°，符号由安装方向决定。

## 步骤 5：确认方向与符号

- [ ] 向"前"倾斜，`pitch` 增大（或减小，记录实际方向）
- [ ] 向"右"倾斜，`roll` 的变化方向符合预期
- [ ] 反转安装方向后，控制方向仍然正确（必要时用 `--axis` 或对调阈值符号）

通过标准：把控制量推过 `--threshold`，控制台出现 `FWD`，反向出现 `REV`，
回到阈值以内出现 `STOP`。

## 步骤 6：测速率与延迟

让它跑满 60 秒，记录 `[stat]`：

```
[stat] r=... p=... y=... age=2.1ms rate=98.4Hz jitter_p95=16.0ms frames=5904 cmd=STOP | ok=5904 bad_sum=0 ...
```

- [ ] `rate` 与设备配置的 ODR 接近（差太多说明连接间隔或主机调度受限）
- [ ] `age` 大部分时间 < 100 ms
- [ ] `jitter_p95` 记录在案，作为控制周期的参考

目标：**控制周期 ≥ (P95 到达间隔 × 2)**，否则控制环大部分时间在重复读同一帧。

延迟实测方法：让传感器做一次快速翻转，同时录屏控制台，数"姿态跳变 → `[CTRL]` 变化"
之间的帧数。要求 < 200 ms（非安全关键场景可放宽）。

## 步骤 7：失效验证（必须做）

| 用例 | 操作 | 通过标准 |
| --- | --- | --- |
| 数据超时 | 保持连接，用 `--stale-timeout 0.5`，然后让传感器超出范围 | 0.5 s 内出现 `STOP valid=False` |
| 断链 | 直接关传感器电源 | 立即出现 `STOP`（`reason=link_down`），随后重连，传感器重启后自动恢复 |
| 程序退出 | `Ctrl+C` | 最后一条指令是 `STOP`，CSV 已 flush，端口已释放 |
| 下游断开 | 开着 `--tcp`，杀掉接收端再重启 | 采集不中断，接收端重连后收到最新指令 |
| 倾角切除 | 把传感器翻到 > 60° | 立即 `STOP invalid`，回到范围内自动恢复 |

## 步骤 8：长跑

- [ ] 连续运行 ≥ 2 小时，`frames` 单调增长，无进程崩溃
- [ ] 期间人为断开 3 次，每次都能自动重连
- [ ] CSV 文件大小合理，行数与 `frames` 一致（抽样核对）

## 排查表

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 扫描不到设备 | 未开机 / 已被手机连接 / 适配器不支持 BLE | 断电重启、关手机 App、换 USB 蓝牙适配器 |
| 能连上，无 `[raw]` | 占用冲突 / UUID 选错 / 设备需使能 | 关掉其他程序；`--dump-hex` 看是否真的没有通知；查厂商资料里的使能指令 |
| `bad_hdr` 持续增长 | 帧类型假设错 | 用 `analyze` 看 id 分布 |
| `bad_sum` 持续增长 | 帧长错 / 误码 | 检查是否 11 字节；缩短距离 |
| 角度整体偏 | 量程比例错 / 未校准 | 按步骤 4 核对；做零位校准 |
| 角度跳变 | 磁场干扰 / 靠近电机 | 远离干扰源；必要时只用加速度+陀螺 |
| 频繁断连 | 省电策略 / 距离 / 干扰 | 缩短距离；关闭 USB 选择性暂停；设备插电 |
| `rate` 远低于预期 | 连接间隔大 / 主机忙 | 用厂商软件把 ODR 与连接间隔调低；减少主机负载 |
