# 技术方案

面向实现者的说明：帧格式、时序决策、失效处理、输出契约，以及"为什么这么写"。

---

## 1. 架构

```
              ┌──────────────── Windows 主机 ────────────────┐
WT9011DCL-BT50│                                             │
   BLE 5.0 ───┼─► BleTransport ──► WitParser ──► TelemetryBuffer
              │   (notify 订阅)   (帧/校验/重同步)   (最新值合并)
              │                                       │
              │                              固定 50 Hz 控制环
              │                                       │
              │                            AttitudeController
              │                            (阈值·滞回·斜坡·失效)
              │                                       │
              │        ┌──────────────┬───────────────┼──────────────┐
              │    ConsoleSink    CsvRecorder    CommandLogSink   TcpSink
              └───────────────────────────────────────────────────┘
                                                          │
                                                   下游：TCP/串口/PLC
```

关键分工：

- **Transport 只管字节**，不解析、不判断。
- **Parser 只管字节 → 物理量**，无状态判断。
- **Buffer 负责"最新值"**，把 11 字节三帧拼成一份完整状态，并记录各字段时间戳。
- **Controller 是纯函数**（输入快照 + 当前时间），所以能被单元测试完全覆盖。
- **Sink 决定指令去哪**，采集侧代码不因下游变化而改动。

## 2. 帧格式

### 2.1 合并帧 `0x55 0x61`（20 字节）

| 偏移 | 长度 | 内容 |
| --- | --- | --- |
| 0 | 1 | `0x55` 帧头 |
| 1 | 1 | `0x61` 类型 |
| 2–7 | 6 | AX, AY, AZ（int16 LE） |
| 8–13 | 6 | GX, GY, GZ（int16 LE） |
| 14–19 | 6 | Roll, Pitch, Yaw（int16 LE） |

换算：

```
accel[g]    = raw / 32768 * accel_range      (默认 16 g)
gyro[dps]   = raw / 32768 * gyro_range       (默认 2000 dps)
angle[deg]  = raw / 32768 * angle_range      (默认 180 deg)
```

**注意**：2 + 18 = 20，没有校验字节。这类帧只能靠"数值落在量程内"做合理性判断，
不能做完整性校验。如果实测发现是 21 字节（末尾多一个校验和），用
`--combined-checksum` 打开校验分支。

### 2.2 分帧 `0x51 / 0x52 / 0x53 / 0x54`（11 字节）

```
55 51 AxL AxH AyL AyH AzL AzH TL TH SUM   # 加速度 + 温度
55 52 WxL WxH WyL WyH WzL WzH TL TH SUM   # 角速度 + 温度
55 53 RollL RollH PitchL PitchH YawL YawH VL VH SUM   # 姿态角 + 版本号
55 54 HxL HxH HyL HyH HzL HzH TL TH SUM   # 磁场 + 温度
SUM = (前 10 字节之和) & 0xFF
```

- 每帧 3 个 int16 + 2 字节附加（温度 /100 °C，或版本号）+ 1 字节校验。
- 这一路**有校验和**，抗误码能力比合并帧强；代价是同一时刻的三类数据来自三帧，
  需要 Buffer 按时间戳合并。

### 2.3 解析器的鲁棒性策略

| 问题 | 处理 |
| --- | --- |
| BLE 分片 / 粘包 | 增量缓冲，凑够帧长才解码 |
| 前导垃圾字节 | 搜索 `0x55`，丢弃之前的字节并计数 |
| 未知类型 | 丢 1 字节重同步，`bad_header++` |
| 校验和错 | 丢 1 字节重同步，`bad_checksum++`（不要整帧丢弃，可能只是错位） |
| 数据洪流 / 异常 | 缓冲区超过 8 KB 只留尾部，`buffer_overflows++` |

统计数据每轮 `[stat]` 打印：`ok / bad_sum / bad_hdr / dropped / overflows`。
联调时这四个数字就是诊断信号：

- `bad_sum` 持续增长 → 波特率/帧长假设错了，或链路误码。
- `bad_hdr` 持续增长 → 帧类型判断错了（比如实际是 `0x51` 分帧却按 `0x61` 解）。
- `dropped` 大但 `ok` 正常 → 正常重同步，可接受。

## 3. 时序设计

### 3.1 为什么控制环不跟着数据走

BLE 通知的到达间隔天然抖动（连接间隔 7.5–15 ms，主机调度、Windows 定时器粒度
约 15.6 ms）。如果"收到数据就算一次控制"，控制周期会随之抖动。因此：

- 通知回调只做两件事：解析、写入 Buffer。
- 控制环用 `asyncio.sleep` 固定 50 Hz，读 Buffer 的**最新快照**。
- 数据比控制周期新即可，控制周期稳定由本地时钟保证。

代价是最多引入一个控制周期（20 ms）的延迟；换来的是确定性的执行节奏。

### 3.2 时间戳

每个样本同时记 `t_mono`（`time.monotonic()`，用于超时判断、不受系统改时间影响）
和 `t_wall`（`time.time()`，用于 CSV 与其他系统对时）。

`age = now - attitude_t` 就是"这份姿态有多旧"。超过 `stale_timeout`（默认 0.5 s）
即判定失效。

### 3.3 带宽与速率估算

- 合并帧：20 B/帧 × 100 Hz = 2 kB/s，BLE 完全够用。
- 分帧：3 帧/周期 × 11 B × 100 Hz = 3.3 kB/s，同样够用。
- 真正的上限通常不是带宽，而是**连接间隔**：一个连接事件通常只能传 1–4 个包，
  所以 100 Hz 需要连接间隔 ≤ 10 ms 且主机调度跟得上。实测以 `[stat] rate` 为准。

## 4. 控制状态机

```
         pitch ≥ +T                    pitch < +T - H
   STOP ──────────► FWD        FWD ──────────────► STOP
     ▲                │
     │                │ pitch ≤ -T
     │                ▼
     └──────────── REV ◄──── pitch > -T + H ──── REV
```

| 规则 | 参数 | 作用 |
| --- | --- | --- |
| 阈值 | `--threshold 15` | 超过 ±15° 才动作 |
| 滞回 | `--hysteresis 3` | 回到 12° 以内才退出，防止临界抖动 |
| 斜坡 | `--slew 2.0` | 指令 0→1 用 0.5 s 爬升，不给执行器阶跃 |
| 超时 | `--stale-timeout 0.5` | 0.5 s 无新姿态 → STOP + `valid=false` |
| 倾角切除 | `--tilt-limit 60` | Roll/Pitch 超 60° 直接 STOP（防翻转/失稳） |
| 加速度门限 | `accel_gate_g`（可选） | 合加速度偏离 1 g 太多 → 判定不可信 |

输出归一化到 `[-1, +1]`，`value` 的正负即方向，绝对值是斜坡后的幅值。

## 5. 失效与恢复

| 事件 | 立即动作 | 之后 |
| --- | --- | --- |
| BLE 断开 | 发 `STOP/valid=false`（不等超时） | 3 s 后重连，失败则 1.5 倍退避，上限 15 s |
| 数据停更 | 超时后 STOP | 数据恢复后自动继续 |
| 倾角越限 | STOP | 回到范围内自动恢复 |
| 用户 Ctrl+C / `--duration` 到点 | 发 STOP | 关闭 CSV、关闭 TCP、退出 |
| 下游 TCP 断开 | 队列继续，重连后补发最新指令 | 队列满时丢最旧（最新状态最重要） |

**关键**：`valid=false` 是与 `value=0` 不同的语义——前者是"我不知道"，后者是"我确认要停"。
下游应把两者都当停机，但日志里要能区分。

## 6. 输出契约

### 6.1 TCP（`--tcp HOST:PORT`）

每行一条，UTF-8，`\n` 结尾；每 200 ms 无变化也会重发最后一条（心跳）：

```json
{"seq":42,"cmd":"FWD","value":1.0,"valid":true,"reason":"hold_fwd","t":1762000000.123}
```

`--tcp-format text` 时改为 `FWD,1.000,42\n`，给不方便解析 JSON 的单片机用。

### 6.2 CSV（`--csv data.csv`）

`t_wall_iso, t_mono, seq, kind, roll_deg, pitch_deg, yaw_deg, ax_g..az_g,
gx_dps..gz_dps, mx..mz, temp_c, cmd, cmd_value`

UTF-8 BOM，Excel 直接打开不乱码；每秒 flush 一次，崩溃最多丢 1 秒数据。

### 6.3 JSONL（`--log-cmd cmd.jsonl`）

只记指令变化（含心跳），每行带 `t_wall`，用于复盘"什么时候发了什么"。

## 7. 性能预期与测量方法

| 指标 | 预期 | 测法 |
| --- | --- | --- |
| 通知速率 | 50–100 Hz（取决于设备配置与连接间隔） | `[stat] rate` |
| 到达抖动 P95 | Windows 上常见 10–20 ms | `[stat] jitter_p95` |
| 控制周期 | 50 Hz ± 定时器误差 | 控制环固定周期，与到达无关 |
| 端到端延迟 | 一个控制周期 + BLE 间隔 + 处理时间 | 打点法：翻转传感器到指令变化的时差 |

## 8. 已知限制

1. 单实例只接一个传感器；多传感器需要多进程（每进程一个 BLE 连接），或改为
   单进程多连接（bleak 支持，但要做好故障隔离）。
2. 没有做姿态融合与滤波：直接用设备输出的欧拉角。需要更平滑时可加一阶低通，
   但会引入相位滞后，控制场景要权衡。
3. 没有实现设备配置写入（改输出速率、改回传内容）。WitMotion 的配置指令是
   `0xFF 0xAA ...` 写入特征值，需要先在实物上确认写入 UUID 再实现。
4. 没有做 Windows 服务化/开机自启，目前是控制台程序。
